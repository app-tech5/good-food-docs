Getting Started

Bring the shared API online first — every mobile and admin client depends on it answering before login or orders work.

Backend API Boot first Self-hosted

What you will achieve

A healthy API process: database reachable, migrations applied, server listening, and a successful login from admin or a mobile app. That is the gate before any storefront or courier demo.

.env keys, migrate commands, port changes, and security notes are in source-docs/my-backend/getting-started.md and the suite launcher source-docs/00-launch-suite.md. This page stays on the boot story.

Before you start the server

  1. Node.js LTS installed — Environment setup.
  2. A MongoDB instance available (local, Docker, or Atlas).
  3. The backend project from your suite ZIP, with secrets copied from the example env file (never commit real secrets).

Soft path to a healthy API

  1. Open the backend project and install dependencies.
  2. Configure database URL, JWT secret, port, and allowed web origins.
  3. Run migrations so collections and demo users exist.
  4. Start the server and confirm it listens (default local port is commonly 5000 unless you changed it).
  5. Point every client (customer, driver, restaurant, admin) at the same host and /api path, then try one login.

If you change the port, update all four clients — mismatched URLs look like “apps are broken” when only the address is wrong.

After it runs — open the suite

  • Admin — Getting Started
  • Customer — Getting Started
  • Restaurant — Getting Started
  • Driver — Getting Started

Feature behaviour (monetization, market, logistics, KDS, intelligence) assumes this API is up — start from each app’s overview, then the feature pages. Deep configuration stays in source markdown.
